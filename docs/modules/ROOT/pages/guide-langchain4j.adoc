= Testing Quarkus LangChain4j Models

include::./includes/attributes.adoc[]
include::./includes/customization.adoc[]

A call to a model is an outbound HTTP request to a provider, and it fails like any other: the provider is down, it hangs, it cuts the response, or it answers `429`.
With a paid model, how the application reacts also decides what a failure costs.

This guide shows how to:

* Address a model, or the AI service that uses it
* Apply faults to a model provider
* Count the prompts that were really sent
* Cut or stall a streamed response
* Fault the chat memory store and the embedding stores behind an AI service
* Fault the MCP servers an AI service calls tools on

The snippets are taken from the `integration-tests/langchain4j` module, some shortened; those of the last two sections from `integration-tests/langchain4j-stores` and `integration-tests/langchain4j-mcp`.
The module runs every scenario against OpenAI, Ollama and Anthropic, each behind an AI service with `@Timeout`, `@CircuitBreaker` and `@Fallback` on the call, talking to small stubs of the chat APIs of the providers.

== Prerequisites

The test class uses the `NetworkFaultsProfile` test profile and injects `NetworkFaults`, as described in the xref:quickstart.adoc[Quick start].

The support for Quarkus LangChain4j is added to the build automatically when `quarkus-langchain4j-core` is present, and that for MCP clients when `quarkus-langchain4j-mcp` is.

== Addressing a Model

Model calls go to `quarkus.langchain4j.<provider>[.<name>].base-url`, and those properties are recognised as targets.
A model is addressed by its bean, or by an AI service that uses it:

[source,java]
----
@RegisterAiService(modelName = "m-openai")
public interface OpenAiSummarizer {

    @UserMessage("Summarize in one sentence: {text}")
    String summarize(String text);
}
----

[cols="2,3",options="header"]
|===
|Target |What it is

|`faults.target(ChatModel.class)`
|The default chat model

|`faults.target(ChatModel.class, ModelName.Literal.of("m-openai"))`
|A named chat model

|`faults.target(OpenAiSummarizer.class)`
|The chat model behind an AI service

|`faults.target(StreamingChatModel.class, ModelName.Literal.of("m-openai"))`
|The same target as the chat model of that name
|===

Embedding, image, moderation, scoring and audio transcription models are addressed the same way, by their bean type and `@ModelName`.

== The Provider Is Down

[source,java]
----
try (ActiveFault f = faults.target(ChatModel.class).unavailable()) {
    when()
            .get("/summarize/default?text=long+text")
            .then()
            .statusCode(503)
            .body(is("model unavailable"));
}
----

`unavailable()` takes the fallback fast, and the circuit breaker is reset when the fault ends.

== The Provider Hangs

[source,java]
----
Target model = faults.target(ChatModel.class, ModelName.Literal.of("m-openai"));
try (ActiveFault f = model.hangs()) {
    long ms = timed(() -> when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503));
    assertTrue(ms >= 1_900,
            "@Timeout alone cannot cut a blocking model call, took " + ms + "ms");
    assertTrue(ms < 9_000,
            "the client timeout must bound the hang, took " + ms + "ms");
}
----

[IMPORTANT]
.`@Timeout` cannot cut a hung model call
====
SmallRye Fault Tolerance interrupts the thread after one second, but the blocking model client keeps waiting, so the caller only gets the fallback when `quarkus.langchain4j.timeout` expires, once per attempt.
That client timeout is the real bound: without it a hung model holds the request as long as the model hangs.

Use the async AI service forms, or set the client timeout, rather than relying on `@Timeout` alone.
====

== The Response Is Cut

[source,java]
----
Target model = faults.target(ChatModel.class, ModelName.Literal.of("m-openai"));
long requestsBefore = model.traffic().httpRequestsSeen();
try (ActiveFault f = model.diesMidRequest(afterBytes(40))) {
    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503);
}
// one attempt plus the retry of the client
assertEquals(2, model.traffic().httpRequestsSeen() - requestsBefore);
----

CAUTION: A cut response costs two prompts. The client of every provider retries once on an I/O error, and a paid model bills both. Only the OpenAI provider exposes `max-retries` to change it.

== The Provider Rate Limits

`http().respondsWith(429)` answers the model call with that status:

[source,java]
----
Target model = faults.target(ChatModel.class, ModelName.Literal.of("m-openai"));
long requestsBefore = model.traffic().httpRequestsSeen();
try (ActiveFault f = model.http().respondsWith(429)
        .contentType("application/json")
        .body("{\"error\":{\"message\":\"rate limited\"}}")) {
    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503)
            .body(is("model unavailable"));
}
// a 429 is retried like an I/O error
assertEquals(2, model.traffic().httpRequestsSeen() - requestsBefore);
----

The status reaches the application as the `RateLimitException` of LangChain4j, and only after the client has retried, so a rate-limited prompt is sent twice too.

With `http().forFirst(1)` the retry succeeds and the caller never sees the `429`:

[source,java]
----
try (ActiveFault f = model.http().forFirst(1).http().respondsWith(429)) {
    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(200)
            .body(is("summary from openai"));
}
----

NOTE: Like every HTTP-aware fault, this needs a plaintext `http://` base URL. Applying it to a model configured with an `https://` base URL throws `UnsupportedOperationException`.

== Counting Prompts

One prompt is one `traffic().httpRequestsSeen()`, so the cost of a failure mode is something a test can assert.
An open circuit breaker, for one, sends nothing:

[source,java]
----
Target model = faults.target(ChatModel.class, ModelName.Literal.of("m-openai"));
try (ActiveFault f = model.diesMidRequest(onNextWrite())) {
    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503);

    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503);

    long before = model.traffic().httpRequestsSeen();
    // breaker open: no prompt sent
    when()
            .get("/summarize/openai?text=long+text")
            .then()
            .statusCode(503);
    assertEquals(before, model.traffic().httpRequestsSeen());
}
----

== Streamed Responses

The streaming form of an AI service, one returning `Multi<String>`, is tested with the moments that read a Server-Sent Events stream.
`StreamingScenariosTest` runs against the OpenAI stub, which answers a streaming request with one event per token:

[source,java]
----
Target model = faults.target(OpenAiStreamingSummarizer.class);
try (ActiveFault f = model.diesMidRequest(afterSseEvents(1))) { // <1>
    when()
            .get("/summarize/stream/openai?text=long+text")
            .then()
            .statusCode(502)
            .body(containsString(" after [summary]"));
}

try (ActiveFault f = model.hangs(afterSseEvents(1))) { // <2>
    when()
            .get("/summarize/stream/openai?text=long+text")
            .then()
            .statusCode(502)
            .body(containsString(" after [summary]"));
}
----

<1> The stream is cut after the first token. A stream cut after tokens were emitted is not retried.
<2> The stream stalls after the first token.

IMPORTANT: `quarkus.langchain4j.timeout` is the read timeout of the REST Client, which does not bound a stalled stream. A model that stops producing tokens is ended only by an idle timeout the consumer of the token stream puts on it. See xref:guide-streamed-responses.adoc[Testing streamed responses].

== Memory and Embedding Stores

The stores an AI service relies on fail like any other dependency, and most of them are a client the extension already proxies: the Redis and MongoDB chat memory stores use a Redis or MongoDB client, the pgvector and Oracle embedding stores a datasource, the Redis embedding store a Redis client.
Their beans resolve to the target of that client, so a fault on the store is a fault on the client behind it, and a test may address either.
Chroma is an HTTP API with an address of its own, `quarkus.langchain4j.chroma[.<store>].url`, which becomes the target `langchain4j:chroma:<store>` and takes the HTTP faults a model does.

[cols="2,3",options="header"]
|===
|Target |What it is

|`faults.target(ChatMemoryStore.class)`
|The client of the chat memory store, `redis:<default>` for the Redis store on the default client

|`faults.target(EmbeddingStore.class)`
|The default embedding store: the datasource behind a pgvector store, `datasource:<default>:jdbc`, the client behind a Redis store

|`faults.target(EmbeddingStore.class, EmbeddingStoreName.Literal.of("c1"))`
|A named store, `langchain4j:chroma:c1` for a Chroma one
|===

The memory is read before the prompt is built, so a chat memory store that is down fails the turn before anything reaches the model, and the model's request count shows it:

[source,java]
----
Target model = faults.target(ChatModel.class);
long promptsBefore = model.traffic().httpRequestsSeen();
try (ActiveFault f = faults.target(ChatMemoryStore.class).unavailable()) {
    when()
            .get("/chat/s1?text=hello")
            .then()
            .statusCode(503);
}
// the memory is read before the model is called: a failed read costs no prompt
assertEquals(promptsBefore, model.traffic().httpRequestsSeen());
----

A hung memory store is bounded by the timeout of its client, `quarkus.redis.timeout` for the Redis one; `quarkus.langchain4j.timeout` plays no part.

The `integration-tests/langchain4j-stores` module runs the Redis memory store, a pgvector store and a Chroma store, all from Dev Services, and checks that each store and the client behind it are one target.

NOTE: With several embedding store extensions in one application, a named store belongs to the extension whose configuration names it, and the default store to the extension whose default store is enabled. When that does not single one out, `target` says so; address the datasource or client behind the store then. The Infinispan, Neo4j, Qdrant, Milvus, Weaviate, Pinecone and Hibernate stores are not recognised yet.

== MCP Servers

An MCP server is a dependency an AI service calls in the middle of a conversation, when the model asks for a tool.
It fails like any other HTTP dependency: it is down, it hangs, it answers with an error.
What differs is where the failure goes.
LangChain4j hands a failed tool back to the model as the tool's result, so the conversation goes on and costs another prompt, and a hung tool call is bounded by the client's `tool-execution-timeout`, which the model call waits for.

The `integration-tests/langchain4j-mcp` module lists and calls the tools of a small stub of an MCP server through the client bean, over the streamable HTTP transport.

=== Addressing an MCP Server

A client over the streamable HTTP or the WebSocket transport is configured with a URL, and that property is recognised as the target `mcp:<client>`:

[source,properties]
----
quarkus.langchain4j.mcp.weather.transport-type=streamable-http
quarkus.langchain4j.mcp.weather.url=http://localhost:8081/mcp
----

The server is addressed by its client bean and `@McpClientName`:

[source,java]
----
Target server = faults.target(McpClient.class, McpClientName.Literal.of("weather"));
----

Every MCP client has a name, so `faults.target(McpClient.class)` alone is refused, and so is the name of a client without a URL: a client over stdio runs a process and has no connection to fault.

=== The Server Is Down

[source,java]
----
try (ActiveFault f = server.unavailable()) {
    when()
            .post("/tools/forecast?city=Athens")
            .then()
            .statusCode(503);
}
----

The client throws, and the resource answers `503`.
Behind an AI service the same failure does not reach the caller: LangChain4j reports it to the model as the result of the tool, and the model answers with that in mind.
Assert on the prompts sent to the model, `traffic().httpRequestsSeen()` on its target, to see what the failed tool cost.

=== The Server Hangs

[source,java]
----
try (ActiveFault f = server.hangs()) {
    long ms = Stopwatch.millis(() -> when()
            .post("/tools/forecast?city=Athens")
            .then()
            .statusCode(503)
            .body(containsStringIgnoringCase("timeout")));
    assertTrue(ms >= 1_900, "the tool call must wait for tool-execution-timeout, took " + ms + "ms");
    assertTrue(ms < 9_000, "tool-execution-timeout must bound the hang, took " + ms + "ms");
}
----

A hung tool call ends when `quarkus.langchain4j.mcp.<client>.tool-execution-timeout` expires: `quarkus.langchain4j.timeout` when that is set, 60 seconds otherwise.
The client does not throw on a timeout.
It returns an error result that says there was one, which an AI service passes to the model like any other tool error, so a resource that calls the client itself has to look at `isError()`.

=== The Server Answers With an Error

[source,java]
----
long before = server.traffic().httpRequestsSeen();
try (ActiveFault f = server.http().respondsWith(500)) {
    when()
            .post("/tools/forecast?city=Athens")
            .then()
            .statusCode(503);
}
assertEquals(1, server.traffic().httpRequestsSeen() - before);
----

=== Counting Tool Calls

One tool call is one request, once the client has a session.
The first use of a client initialises it, two requests over the streamable HTTP transport, so a test that counts warms the client up first, with a `listTools()` for example.
Two settings keep the count to what the test sends:

* `auto-health-check=false`, or the client pings the server every `auto-health-check-interval`, 60 seconds by default
* `protocol-version`, or the client probes the server for the newest protocol it supports before it initialises

== Summary

What the tests established, identically for all three providers:

* Calls go through the proxy and are counted
* `unavailable()` takes the fallback fast, and the breaker is reset when the fault ends
* A cut response and a `429` each cost two prompts, because every client retries once
* An open breaker sends nothing
* `@Timeout` cannot cut a hung model call; `quarkus.langchain4j.timeout` is the real bound
* A chat memory store that is down fails the turn before a prompt is sent; a hung one is bounded by its client's timeout
* An MCP server is addressed by its `McpClient` bean and `@McpClientName`; a hung tool call is bounded by `tool-execution-timeout`, and the client returns an error result rather than throwing
